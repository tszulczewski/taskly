# Task list

`import { TaskList } from "@taskly/ui";`

## 1. What it is for

Shows every task of the renovation on one calm surface, with subtasks under their task, so the owner sees what is left and what it may cost. It also covers the moments without a list: loading, a failed load and no tasks yet.

## 4. Anatomy

| Part          | Required | Notes                                                                |
| ------------- | -------- | -------------------------------------------------------------------- |
| Surface       | yes      | One `Surface` as `<ul aria-label="Tasks">` (R02.1)                   |
| Rows          | yes      | `TaskRow` per task, divided by 1px lines; subtasks nested in the row |
| Loading       | state    | Three skeleton rows, `aria-busy`, a hidden "Loading tasks…" status   |
| Error         | state    | `ErrorState`: "Could not load your tasks." and "Try again"           |
| Empty         | state    | `EmptyState`: "No tasks yet. Add the first thing you need to do."    |
| Delete dialog | yes      | One `DeleteTaskDialog` for the list                                  |
| Order         | optional | With `onMove`: tasks move in the list, subtasks in their task (G1)   |
| Completion    | optional | With `onToggleComplete`: checkboxes, one `CompleteTaskDialog` (E03)  |

## 5. Variants

None. What it shows depends on `status` and `tasks`. `onMove`, `onToggleMarker` and `places` turn on ordering, markers and places (E02); the app passes them together. `onToggleComplete` turns on completion (E03).

## 7. Behaviour and accessibility

- A list named "Tasks"; each subtask list is named "Subtasks of “…”", so a screen reader announces the nesting and the count.
- Loading is announced once by the status text; the skeleton is hidden (WCAG 4.1.3).
- After a delete the list itself takes focus (`tabindex="-1"`), because the row and its "…" are gone; after Cancel focus returns to "…" (spec E01: "returns focus to the trigger"). After the last task is deleted the empty state takes focus instead (`tabindex="-1"`, decision O4).
- The page scrolls; the list never gets its own scroll area.
- With `onMove` the list (and each task's subtasks) is one sortable group; moves are announced by title (see Drag handle). Pending rows never move, so no temporary id reaches the server. Completed rows never move either (decision 2026-10-21).
- With `onToggleComplete` the list receives tasks already sorted by the server (open, then completed). When a row changes place it slides there over `motion-duration-base` (instant with reduced motion) and focus stays on its checkbox; the dialog's Cancel returns focus there too.

## 11. Code

```tsx
const tasks = useTasks(listId);

<TaskList
  status={tasks.isPending ? "loading" : tasks.isError ? "error" : "ready"}
  tasks={tasks.data?.map(toTaskItem) ?? []}
  onRetry={() => tasks.refetch()}
  retrying={tasks.isRefetching}
  validate={validateTaskForm}
  onEdit={(id, values) => updateTask.mutateAsync({ id, ...values })}
  onAddSubtask={(parentId, values) => createTask.mutateAsync({ ...values, parentId })}
  onDelete={(id) =>
    deleteTask.mutateAsync(id).then(
      () => true,
      () => false,
    )
  }
  highlightId={lastAddedId}
  onMove={(id, { afterId, beforeId }) => moveTask.mutate({ id, afterId, beforeId })}
  onToggleMarker={(id, marker, on) => setMarker.mutate({ id, marker, on })}
  places={placeOptions}
/>;
```
