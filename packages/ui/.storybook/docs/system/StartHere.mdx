# Start here

Taskly helps one person plan a home renovation: a list of tasks, what each may cost, and what is still ahead. This system holds everything a screen is built from: tokens, primitives, product components, patterns and full screens. Read this page first, then the page of each part you use.

## Character

Taskly is a quiet list for someone in the middle of building work: it shows what to do next and what it may cost, and nothing else asks for attention. It speaks plainly, in short sentences, about tasks, places and money, never in the language of software teams. Colour is spent on two things only, actions and "completed", so the little colour there is always means something.

| Is                                                             | Is not                                                                   |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **simple**, **readable**, **sparing** (in colour and ornament) | **loud** (bright bars, saturated surfaces)                               |
| **matter-of-fact**, **calm**                                   | **scattered** (many panels and windows), **overloaded**                  |
|                                                                | **technical** (ids, jargon), **generic** (the look of any generated app) |

Source: `.ai/design/reference.md` (character and anti-character words, confirmed by the owner 2026-10-21).

## Build a screen in five steps

1. **Find the pattern.** Start from the closest pattern (Patterns: Form, List, Details in row, Quick capture, Inline edit, Delete confirmation, Optimistic change, Reorder, Complete and reopen) and the closest screen (Product / … / Screens). Copy its structure, not its data.
2. **Choose components with [How to choose](?path=/docs/design-system-how-to-choose--docs).** Use the table below; open each component's page for its states and API. If nothing fits, read [What is missing](?path=/docs/design-system-what-is-missing--docs) before building anything new, then [Contributing](?path=/docs/design-system-contributing--docs).
3. **Use semantic tokens only.** Colours, sizes, spacing, radius and motion come from the tokens through Tailwind utilities (`bg-list`, `text-muted`, `gap-group`, `p-inset`, `duration-base`). No hex, no Tailwind palette class (`text-gray-500`), no arbitrary value (`p-[13px]`). `npm run check:tokens` fails on any of them. See Foundations.
4. **Design every data state.** Loading, empty, failed, partial data, many items, long text; for forms also pending, field error, server error and offline. Each state is its own story, and the screen gets a state map (which story shows which state).
5. **Check [What to avoid](?path=/docs/design-system-what-to-avoid--docs).** Then check the screen at 320, 768 and 1440 px, in both themes, with the keyboard only.

## All components

Product components are presentational (decision P1): props in, callbacks out, amounts arrive formatted; the app wires them to TanStack Query and `@taskly/core`.

## How to read the sources

Every rule in these pages names where it comes from. A rule without a source is marked as a proposal.

| Id                                                                     | Where                                                                                      |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| R01.x, R02.x, A01.x–A05                                                | references and anti-references, `.ai/design/reference.md`                                  |
| Q1–Q5, P01–P15, Luki 1–10                                              | the owner's answers, proposals and gaps in `.ai/design/reference.md`                       |
| T1–T10, tokens rule 1–15                                               | `.ai/design/tokeny.md` (decisions and "Zasady")                                            |
| D01–D21, R06–R11, N01–N04                                              | product decisions and rules, `.ai/specs/product-brief.md`                                  |
| spec E01, sign-in spec                                                 | `.ai/specs/2026-10-16-tasks-and-subtasks.md`, `.ai/specs/2026-10-16-sign-in-pages.md`      |
| E01-S01 … E03-S02                                                      | backlog stories, `.ai/specs/backlog.md`                                                    |
| decision 2026-10-21                                                    | completed tasks' order, `.ai/specs/research/decisions/2026-10-21-completed-tasks-order.md` |
| P1–P5, K1–K5, B1–B9, C1–C10, D1–D10, E1–E12, F–J, L1–L4, M1–M5, N1–N11 | decisions taken while building this system, `packages/ui/POSTEP.md`                        |
| standards §N                                                           | `.ai/docs/engineering-standards.md`                                                        |
| task rule N                                                            | the rules of the task that built this system, `.ai/design/prompt-storybook.md`             |
| WCAG x.y.z, WAI-ARIA APG                                               | the accessibility standard and its authoring practices                                     |

Note the two families that look alike: **P01–P15** (reference proposals, two digits) and **P1–P5** (stage-0 decisions); **R02.x** (a reference row) and **R06–R11** (product rules).

## Commands

| Command                                  | What it does                                                 |
| ---------------------------------------- | ------------------------------------------------------------ |
| `npm run storybook -w packages/ui`       | Storybook on port 6006                                       |
| `npm run build-storybook -w packages/ui` | static Storybook in `packages/ui/storybook-static`           |
