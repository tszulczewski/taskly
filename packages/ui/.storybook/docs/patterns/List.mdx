# List

How Taskly shows a collection, shown on the task list: one calm surface, a row per item, and a clear answer for every moment without items. Built from `TaskList`, `TaskRow`, `Skeleton`, `EmptyState` and `ErrorState`.

## Rules

| Rule                                                                                                                 | Source            |
| -------------------------------------------------------------------------------------------------------------------- | ----------------- |
| One `Surface`, rows divided by 1px lines; no card per item, no panel in a panel.                                     | R02.1, A01.3, A02 |
| A row is one line: what it is on the left, the amount on the right, actions behind "…".                              | R02.1, R02.5, P2  |
| First load: static skeleton rows in the shape of real rows and one "Loading…" status. Never a spinner over the page. | spec E01, Luki 8  |
| Later loads keep the data on screen.                                                                                 | proposal C3       |
| A failed load replaces the list with what failed and "Try again"; nothing else on the page breaks.                   | spec E01          |
| Empty says why it is empty and the next step, in words; focus goes to the place where that step happens (quick add). | spec E01, Luki 5  |
| Missing data in a row is said in words ("No estimate"), never left blank.                                            | spec E01, R10     |
| The page scrolls; the list never gets its own scroll area.                                                           | WCAG 1.4.10       |
| Everything completed: no message; the muted, struck-through rows say it (success needs no words).                    | P3, decision N10  |

## A list that is not tasks

Version 1 has only the task list; the quick shopping list (E04) will be the second. Until a shared row component exists (decision N1: it is built with the E04 spec), build such a list from primitives with `TaskRow`'s layout. Do not use `TaskList` or `TaskRow` for it: they always show an estimate ("No estimate") and the task menu.

| Row         | `li` with `border-t border-divider first:border-t-0`; inside it `flex min-h-row items-start gap-group px-inset py-row-y hover:bg-raised`                                                                                                                                                                                                                        | decisions N1, N2                              |
| Done        | `Checkbox` with an `id` and a visible `Label` holding the item's name; done = the name in a `span` with `text-muted line-through` inside the `Label`; regular weight                                                                                                                                                                                            | decisions N5, N6                              |
| Text block  | `flex min-h-touch min-w-0 flex-1 flex-col justify-center`: centred against the 44px checkbox while it fits; a longer name grows downwards and the box stays at the top (Checkbox › Content). While pending, a `text-meta text-muted` line "Saving…" under the name, the checkbox disabled and the items of "…" disabled (the menu still opens), as in `TaskRow` | Optimistic change, decisions F3, U1           |
| Actions     | one "…" `Menu` inside a `Tooltip`, with the same `aria-label` on `MenuTrigger` and on the `Button`; Delete last, after a separator. A done item keeps Edit and Delete, like a completed task                                                                                                                                                                    | decisions N4, I3, O5, Menu                    |
| Row message | under the name, past the checkbox column (a `w-touch` spacer), `role="alert"`, `text-meta text-danger`, `pb-row-y`                                                                                                                                                                                                                                              | Optimistic change                             |
| New item    | shown at once, pending, after the open items; once the server confirmed, `row-highlight` on its line and `scrollIntoView({ block: "nearest" })`, without smooth scrolling under reduced motion; the add field keeps focus                                                                                                                                       | Optimistic change, Quick capture, decision F1 |
| Order       | open items first, done ones after them; a new item goes after the open items, before the done ones; an item unchecked goes back to the top. It jumps to its place; only `TaskList` slides rows. After a tick the row moves: focus stays on its checkbox (put it back after the move, as `TaskList` does)                                                        | decision 2026-10-21, N5, N9, WCAG 2.4.3       |

## Empty versus no results

**Empty** means nothing exists yet: "No tasks yet. Add the first thing you need to do." **No results** would mean items exist but a filter hides them. Version 1 has no filters (P03, P4), so there is no no-results state yet. When filters arrive, it must name the filter and offer to clear it, and never reuse the empty text (proposal).
