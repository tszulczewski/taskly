- **Task 2.1 (optional response schemas, first half of spec step 7).** `@taskly/core` (`http.ts`): `ResponseSchema<T>`, a structural type with only `safeParse` (the app has no `zod` dependency, as `form-errors.ts` already keeps it), and `apiResponseSchema`, the envelope as a discriminated union on `ok` (`data` optional; error `code`/`message` strings, optional `fieldErrors` as `Record<string, string[]>`). Server: `apiHandler(fn, { response })`; the schema also types the handler result (`NoInfer`, so it comes from the schema). The result is checked with `safeParse` inside the existing `try`; a failure throws a private `OutputContractError` (not a `ZodError`, so `mapError` gives the generic 500 and never the 400 path) and is logged as the single string `Response failed its output contract: <METHOD> <pathname>` (no query string, no error object, no values). The **parsed** value is serialized, so unknown keys are stripped and an internal field a service adds by mistake never leaves the server. Client: `apiCall(path, { …init, response })` returns the parsed `data` typed from the schema (overloads; without `response` it still returns `data` unchecked as `T`). The envelope goes through `apiResponseSchema`, and the envelope kind must agree with `res.ok` (a success envelope on a 5xx or an error envelope on a 2xx is `bad_response`); a malformed envelope, a non-JSON body or data failing the schema all throw `ApiError(status, "bad_response", "Unexpected server response")`. `response` is never passed on to `fetch`. No existing caller used either helper outside their tests (the auth route uses Better Auth's handlers, the forms use `authCall`), so nothing else changed.
