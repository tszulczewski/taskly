Rules decided here (the spec gives only the examples): leading/trailing whitespace (any Unicode whitespace, `trim()`) is ignored; whole złoty are either plain digits (leading zeros allowed, "007") or grouped by exactly three with a space, NBSP or narrow NBSP (U+202F; mixed separators allowed); a grouped amount must not start with 0 ("0 500" rejected); then an optional `,` or `.` with 1–2 digits. - Task 1.4: no deviation from the spec. Open point, not a regression: two *different* managers of one list deleting it at the same moment can still deadlock (each holds its own membership `FOR UPDATE` from `requireRole`, then waits for the other's in the all-members lock); the old code had the same cycle. It cannot happen today, since only `createList` and `ensureDefaultList` create owners and invitations never grant `owner`, so a list has one owner. If co-owners ever arrive, `deleteList` could skip `requireRole`'s lock and take all memberships in one ordered statement after an unlocked role check, or retry on `40P01`.
- Task 1.5: no deviation from the spec. `requireTaskRole` is exported from `tasks.ts` and therefore from `@taskly/core/server` (tests call it directly; `requireRole` is exported the same way). `createTask` for a non-member reports `NotFoundError("List")` (the route is list-scoped), while `requireTaskRole` reports "Task". `listTasks` also runs through the error translation, which is harmless for a read. The real `createTask` cannot be paused between `requireRole` and its list lock while the delete holds the list row, so the fix itself stays pinned by the 1.4 hand-written test (see Verification); with the holder on the list row, the editor is ahead of the delete in the list row's lock queue, so `pg_blocking_pids` also reports the editor as blocking the old delete (a "soft block").

The new `deleteTask`/`deleteList` tests pin the outcomes (no `40P01`, `null` or 404, nothing left), not the all-members lock: with the old `deleteList` the cascade blocks on the editor's membership before it touches `tasks`, and `deleteTask` never locks the list row, so even an editor paused between `requireRole` and its task lock forms no cycle.
